# Analysis endpoint: suspicious network/web scanning

The suspicious network scanning activity scenario follows the general analysis-endpoint architecture in ARC-009.

## Input data structure
RADAR's scanning detection scenario considers the following detection criteria for potentially malicious web-scanning:

- HTTP requests carrying a "User-Agent" string associated with a known scanning tool (e.g. sqlmap, nikto, nmap)
- An abnormal rate of failed HTTP responses (401/403/404) from the same source IP within a short window
- Use of HTTP methods a normal client would not send (e.g. TRACE, PROPFIND).

We design DECIPHER to be compatible with RADAR's alert information, which we consider that contains a generic enough baseline of IOCs for web scanning. Thus, the alert data structure received as input for the CTI analysis is conformed of:

| Field | Type | Required | Description |
|---|---|---|---|
| `src_ip` | `list[str]` | Y | IP address of the source of the scanning activity |
| `uri` | `list[str]` | Y | The requested (probed) URI path(s) |
| `user_agents` | `list[str]` | Y | Observed 'User-Agent' string(s) in the HTTP request |
| `http-method` | `list[str]` | N | The HTTP method(s) requested |
| `target_host` | `str` | N | Name of the scanned endpoint (for context only; not an IOC) |
| `timestamp` | `datetime` | N | ISO 8601 timestamp of the detected activity |

In addition, the `detection_chain` field of type `list[(int,str)]` can be used to provide a chronologically ordered list of detection rules (Wazuh rules for now) that resulted in the alert being triggered (e.g. burst $\rightarrow$ scanner UA $\rightarrow$ confirmed scan $\rightarrow$ exploitation pattern), as specified in SRS-060.

**Example of alert**
```
alert_data = {
    "src_ip": ["203.0.113.42"],
    "uri": ["/wp-login.php", "/admin/config.php"],
    "user_agents": ["sqlmap/1.7.2#stable (http://sqlmap.org)"],
    "http_method": ["TRACE", "PROPFIND"],
    "target_host": "owncloud.abc.lu",
    "timestamp": "2026-08-24T10:15:32Z",
    "detection_chain": [(1, "burst"), (2, "scanner UA"), (3, "confirmed scan")]
}
```

## IOCs in MISP

Conveniently, the MISP object `http-request` encapsulates all the relevant information from the alert. The alert fields map to the object's attributes as follows:

| Alert field | `http-request` attribute |
|---|---|
| src_ip | ip-src |
| uri | uri |
| user_agents | user-agent |
| http_method | http-method |
| target_host | hostname |

Ideally, we would like to find `http-request` objects containing more than one of the indicators.

The way of ingesting CTI in MISP is far from standard, thus, we also search for MISP events containing the alert IOCs mapped to the same MISP attribute types without an object.

The `research-scanner` MISP object is another relevant structure, used for reporting known scanning activity, e.g., from a known ongoing research project. Useful fields are: domain, project, scanning_host, scanning_ip, scheduled_start, scheduled_end and contact_email.

### MISP warninglists
[MISP warninglists](https://github.com/misp/misp-warninglists) are lists of well-known indicators that can be associated to potential false positives, errors or mistakes.

Malicious scanning is hard to distinguish from legitimate internet-wide research or benign scanning services (e.g. Shodan, Censys, academic research projects), since a source IP can appear in a threat feed and in a "known scanner" reference at the same time. To surface that context to the analyst without discarding genuine findings, the alert's `src_ip` values are additionally checked against misp-warninglists (a match returns the name of the matching list) and against `research-scanner` objects' `scanning_ip` attribute (a match returns the object's `project` or `domain` attribute).

Warninglists are used exclusively for this contextual lookup. MISP's `enforceWarninglist` search parameter, which removes attributes hitting an enabled warninglist from the search results, is disabled for this scenario.

### Scoring tags

MITRE ATT&CK galaxy tags relevant to this scenario:
- T1595.002 vulnerability scanning,
- T1595.003 wordlist scanning

## Analysis report

When a MISP instance is available and reachable and MISP search is enabled in the configuration, the analysis report must include the field `identified-scanners` of type `dict[str, list[str]]`, mapping a source IP to the sources it was found in. This field can contain:

(a) an entry per matched source IP, holding the name of every matched misp-warninglist and/or research-scanner project or domain for that IP, or

(b) an empty mapping when no match with registered scanners is found, which can be signaling a malicious scanning source.

By design, a match on `identified-scanners` is contextual only; it does not alter the severity score computed by the scoring engine as suppressing or discounting the score on a match would risk masking potential threats from a compromised benign source.

When MISP is unavailable or disabled in DECIPHER's configuration, the `identified-scanners` field must not be present.
