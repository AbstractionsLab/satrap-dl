# DECIPHER analysis outcome status

_As a_ consumer of DECIPHER analysis results (e.g. RADAR), _I want_ every analysis response to carry a single status code/flag summarizing the outcome of the CTI enrichment, _so that_ I can identify in a straightforward way what happened during the analysis execution (e.g. MISP available or not, lookup errors, etc.).

I want the analysis status to:

1. Be a top-level field of every analysis response, applied uniformly to all threat scenarios.
2. Report one of the following values, with a self-describing identifier:
	- MISP available and CTI found;
	- MISP available and no CTI found;
	- MISP unavailable or unreachable;
	- MISP disabled (in the runtime configuration);
	- MISP lookup error: MISP was reached but the query failed (e.g. API error, unparseable response).
3. Be extensible with new values (e.g. benign-evidence states) without changing the meaning of existing ones.

The status applies only to valid requests (as per SRS-050); requests with invalid field values return input errors and no analysis is run.

The `misp_available` field of the analysis report is deprecated in favor of this status.

### Rationale
To capture the output of the analysis execution in one semantic item and provide it as a single machine- and human-readable code. The status code covers only the cti enrichment outcome; the outcome of case creation is handled separately.

### Acceptance criteria
1. When MISP is reachable and threat intelligence is found for at least one alert IOC, the status indicates MISP available and CTI found.
2. When MISP is reachable and no threat intelligence is found for any alert IOC, the status indicates MISP available and no CTI found.
3. When the connection to MISP fails at request time (connection refused, timeout, authentication failure, or TLS failure), the status indicates only MISP unavailable or unreachable.
4. When MISP search is disabled in the runtime configuration, the status indicates MISP disabled.
5. When MISP is reached but the query fails (API error or unparseable response), the status indicates MISP lookup error.
6. A request with no information in a mandatory field returns an HTTP validation error with details and no query is sent to MISP.
7. For every supported threat scenario, the status is present at the top level of the analysis response, and its value is the same whether case creation is enabled, disabled, or fails.
8. The API schema marks the `misp_available` report field as deprecated.
9. The service health check reports the same result whether MISP is reachable or not.
