# Threat scenario analysis: suspicious web scanning

_As a_ security engineer, _I want to_ use DECIPHER to obtain a CTI-based severity score for detected network scanning alerts, _so that_ I can distinguish malicious scanning from known-legitimate scanning and prioritize my triage accordingly.

To run an analysis for this threat scenario, I want to:

1. Make a POST request to the DECIPHER analysis endpoint with the `suspicious_nt_scanning` alert/threat scenario identifier.
2. Include in the body of my request: the IP(s) of the scanning activity source, the requested URI path(s), and the observed User-Agent string(s); optionally: the used HTTP method(s), the target host name or ip, and the timestamp of the alert.

I want the DECIPHER REST service to:

- implement the analysis endpoint logic defined in SRS-050, applied to suspicious network scanning alerts,
- report when the alert's source IP corresponds to a known, likely-legitimate scanning source (e.g. a recognized security research project or public scanning service), naming the matching source so I can apply my own judgement.

A match against a known, likely-legitimate scanning source must not alter the severity score. This implies that threat intelligence about a known-scanner indicator is considered for computing the score and the matches are reported separately.

### Rationale
To reduce alert fatigue by automating the triage and escalation of web scanning incidents, ensuring that responders only handle cases supported by threat intelligence evidence and receive the context needed to act immediately.

Distinguishing malicious scanning from legitimate internet-wide research or benign scanning services (e.g. Shodan, Censys) is a well-known precision problem for this threat scenario; reporting a match against known, likely-legitimate scanning sources explicitly lets the analyst apply that judgment without suppressing genuine findings, since a source IP can simultaneously belong to a known scanning service's range and pose a genuine malicious threat (e.g. compromised infrastructure repurposed by an attacker).

### Acceptance criteria
Assuming that a MISP instance is running, reachable, and enabled in the DECIPHER REST service:

1. A POST request to the DECIPHER analysis endpoint with the `suspicious_nt_scanning` identifier and a body containing source IP, uri, and user-agent strings, triggers the analysis pipeline and returns a structured analysis result with a severity score and a score breakdown.
2. When events related to the given IOCs are found in MISP, the resulting severity score is non-zero. If case creation is enabled in the runtime configuration file, a prioritized Flowintel case is created and the id and url returned as part of the analysis response.
3. The analysis response contains a field mapping each source IP that corresponds to a known, likely-legitimate scanning source reported in MISP to the names of the matching sources. If no such matches are found, this field is returned empty.
4. The severity score is identical whether or not the matching sources are registered in MISP.
5. A case created in step 2 has a priority tag consistent with the computed severity score and the configured escalation thresholds, and a description including the alert data, the contributing indicators with evidence, the score breakdown, and matching scanners.
6. When no matching threat intelligence is found for any of the alert IOCs, the severity score is 0, regardless of whether the source IP corresponds to a known, likely-legitimate scanning source.
5. Analysis requests with incomplete alert data or incorrect data types return an error message indicating the cause.
7. When the MISP service is unavailable or disabled, the returned analysis report has severity 0 and an informative error message. The response does not include the field described in point 3 above as such information is meaningful only when a MISP search actually had place.
