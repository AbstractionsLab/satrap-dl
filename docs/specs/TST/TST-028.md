# Test analysis endpoint core behavior

Validate the core behavior of the analysis endpoint: request and response structure, input validation, error handling, case creation configuration, and the reporting of the CTI lookup result (`cti_lookup_result`).

## Preconditions
- Docker Engine (or daemon) running with execution privileges for the testing user
- A shell with `curl` installed
- MISP and Flowintel instances running
- The DECIPHER REST service is not running
- A user with `User` role created in MISP and an API key generated for that user

## Setup actions
1. Follow the configuration instructions in the README of DECIPHER (`/decipher/README.md`) and ensure that:
    - The MISP and Flowintel instances are set in `config/decipher-settings.yaml` with valid API keys.
    - `config/decipher-runtime-cfg.yaml` and `config/decipher-scoring-cfg.yaml` exist with the default values.
2. Bring the DECIPHER service up and ensure it is reachable at http://localhost:8000 (*Note: if a different host/port is used for the REST service, update the curl commands accordingly*)

	```
	./decipher_up.sh --api
	```


## Test steps

### Successful analysis with valid data (SRS-050 AC1, SRS-061 AC7)

1. Send a POST request to the `suspicious_login` analysis endpoint with valid alert data:

```
curl -w " HTTP %{http_code}" \
  -X 'POST' \
  'http://localhost:8000/api/v1/analyze/suspicious_login' \
  -H 'accept: application/json' \
  -H 'Content-Type: application/json' \
  -d '{
  "username": "jdoe",
  "target_host": "192.168.1.10",
  "src_ips": ["10.0.0.1", "10.0.0.2"],
  "timestamp": "2026-03-10T08:30:00Z"
  }'
```

### Analysis endpoint with invalid data (SRS-050 AC2)

1. Send a POST request to the analysis endpoint with structurally invalid data (e.g., missing required fields):

```
curl -w " HTTP %{http_code}" \
  -X 'POST' \
  'http://localhost:8000/api/v1/analyze/suspicious_login' \
  -H 'accept: application/json' \
  -H 'Content-Type: application/json' \
  -d '{
  "username": "jdoe",
  "target_host": "192.168.1.10"
  }'
```

### Analysis endpoint with unregistered alert type (SRS-050 AC3)

curl -w " HTTP %{http_code}" \

### Internal analysis failure (SRS-050 AC4)

1. Corrupt `config/decipher-runtime-cfg.yaml` with invalid YAML content. For example, replace the line:

```json
analysis:
```
with
```json
analysis: x
```
2. Send a POST request with valid alert data to the analysis endpoint.
```
curl -w " HTTP %{http_code}" \
  -X 'POST' \
  'http://localhost:8000/api/v1/analyze/suspicious_login' \
  -H 'accept: application/json' \
  -H 'Content-Type: application/json' \
  -d '{
  "username": "jdoe",
  "target_host": "192.168.1.10",
  "src_ips": ["10.0.0.1"],
  "timestamp": "2026-03-10T08:30:00Z"
  }'
```
3. Verify that the response contains the string `HTTP 500` and that its `detail` is a generic message that does not contain internal error details (e.g. no YAML parser messages or file paths).
4. Inspect the DECIPHER service log (e.g. `docker logs decipher-api-1`) and verify that it contains the details of the internal error.
5. Restore `config/decipher-runtime-cfg.yaml` to its original state by deleting the added `x`.

### Case creation enabled (SRS-050 AC5, SRS-061 AC7)

1. Set `enable_case_creation: true` in `config/decipher-runtime-cfg.yaml`.
2. Send a POST request with valid alert data:

```
curl -w " HTTP %{http_code}" \
  -X 'POST' \
  'http://localhost:8000/api/v1/analyze/suspicious_login' \
  -H 'accept: application/json' \
  -H 'Content-Type: application/json' \
  -d '{
	"username": "testuser",
	"target_host": "192.168.1.10",
	"src_ips": ["10.0.0.1"],
	"timestamp": "2026-03-10T10:00:00Z"
	}'
```
3. Verify that the response shows `HTTP 200`, the `created_case.id` is non-zero and the case with the returned ID exists at the URL returned in `created_case.link`.
4. Verify that the description of the case contains the following sections:
	- Scenario: with reference to suspicious login
	- Alert information: the data corresponds to data sent in the POST request
	- Severity score
	- Score breakdown
	- Additional information: including log_summary, misp_available and misp_events_found rows.
5. Record the value of the top-level `cti_lookup_result` field of the response as `<cti-result-case-enabled>`.

### Case creation disabled (SRS-050 AC6, SRS-057 AC2, SRS-061 AC7)

1. Set `enable_case_creation: false` in `config/decipher-runtime-cfg.yaml`.
2. Send the POST request of step 2 in "Case creation enabled".
3. Verify that the response status is HTTP 200.
4. Verify that `created_case.id` is 0 and `created_case.link` is an empty string.
5. Verify that the `report` contains a message indicating that case creation is disabled in the `log_summary`.
6. Verify that the top-level `cti_lookup_result` field of the response is equal to `<cti-result-case-enabled>`.

### MISP search disabled (SRS-050 AC7, SRS-057 AC1, SRS-061 AC4)
1. Set `enable_misp_search: false` in `config/decipher-runtime-cfg.yaml`.
2. Send a POST request with valid alert data (e.g. the one in "Successful analysis with valid data").
3. Verify that the response status is HTTP 200.
4. Verify that the `severity` field of the response is 0.
5. Verify that the top-level `cti_lookup_result` field of the response is `misp_disabled` and that the deprecated `report.misp_available` entry is `False`.
6. Verify that the `report.log_summary` field of the response indicates that MISP search is disabled.

### Mandatory fields without information (SRS-061 AC6)

1. Send a POST request in which the mandatory string field `username` contains only whitespace:

```
curl -w " HTTP %{http_code}" \
  -X 'POST' \
  'http://localhost:8000/api/v1/analyze/suspicious_login' \
  -H 'accept: application/json' \
  -H 'Content-Type: application/json' \
  -d '{
  "username": "  ",
  "target_host": "192.168.1.10",
  "src_ips": ["10.0.0.1"],
  "timestamp": "2026-03-10T08:30:00Z"
  }'
```

2. Send a POST request in which the mandatory list field `src_ips` contains only empty or whitespace-only strings:

```
curl -w " HTTP %{http_code}" \
  -X 'POST' \
  'http://localhost:8000/api/v1/analyze/suspicious_login' \
  -H 'accept: application/json' \
  -H 'Content-Type: application/json' \
  -d '{
  "username": "jdoe",
  "target_host": "192.168.1.10",
  "src_ips": ["", " "],
  "timestamp": "2026-03-10T08:30:00Z"
  }'
```

## Expected outcome

**Successful analysis with valid data:** The printed output contains the string `HTTP 200` and a JSON response containing the following fields: `"analyzed_scenario": "suspicious_login"`, `cti_lookup_result`, `severity`, `report`, and `created_case`.

**Analysis endpoint with invalid data:** The printed output contains the string `HTTP 422` and the response body contains an invalid data message and a list of validation errors with details, identifying `src_ips` and `timestamp` as missing fields.

**Analysis endpoint with unregistered alert type:** The printed output contains the string `HTTP 404` and a message informing about an unknown alert type.

**Internal analysis failure:** The validations in steps 3 and 4 succeed.

**Case creation enabled:** Steps 3 and 4 are successfully validated, and `<cti-result-case-enabled>` is one of `cti_found`, `no_cti_found`, `misp_lookup_error`, `misp_disabled` or `misp_unavailable`.

**Case creation disabled:** The validations from steps 3 to 6 succeed.

**MISP search disabled:** The validations from steps 3 to 6 succeed.

**Mandatory fields without information:**

1. The printed output contains the string `HTTP 422`, and `detail.errors` contains an entry whose `loc` is `["username"]` with a message asking for at least 1 character.
2. The printed output contains the string `HTTP 422`, and `detail.errors` contains an entry whose `loc` is `["src_ips"]` with a message stating that the list must contain at least one non-empty string.
