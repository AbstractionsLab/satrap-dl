# Test analysis scenario: suspicious web scanning

Validate the scenario-specific behavior of the `suspicious_nt_scanning` threat scenario: the reporting of known, likely-legitimate scanning sources in the `identified-scanners` field, the invariance of the severity score with respect to those matches, and the default case creation decision.

The behavior shared by all analysis scenarios (request and response structure, unknown alert type, internal failures, and the `enable_case_creation` and `enable_misp_search` toggles) is covered by TST-028 and is not repeated here.

## Preconditions
- DECIPHER stack running (`cd deployment && ./decipher_up.sh --all`)
- A reachable MISP and Flowintel instance set in `config/decipher-settings.yaml` with valid API keys for a `User` role (MISP).
- `config/decipher-runtime-cfg.yaml` with the following settings:
    - `enable_misp_search: true`
    - `enable_case_creation: true`
    - `event_timestamp: 7d`
    - `enforce_warninglist: true`
- Access to a shell with `curl` and `jq`
- A MISP user with `Admin` role and an API key for this user
- The MISP attribute `71.6.199.23` of type `ip-src` is not present in the MISP instance (check with "Event actions" $\rightarrow$ "Search attributes").

## Setup actions
1. Login with an `Admin` user into MISP and ensure that the following taxonomies are enabled ("Event actions" $\rightarrow$ "List taxonomies"): admiralty-scale, tlp, type.
2. Enable warninglists related to public scanning services (in case of error, check the name of the decipher running container with `docker ps`):

```sh
docker exec decipher-api-1 \
  python -m decipher.tools.warninglists_mgr enable --api-key <misp-admin-key>
```

3. From the project root folder, go to `tests/decipher/runners` and update the `push_misp_events.sh` script with the URL and the API key of your MISP instance.
4. Run the script to create the web scanning test events in MISP:

```sh
cd tests/decipher/runners
./push_misp_events.sh
```

5. Login into MISP with the test user and verify that the 6 events defined in `tests/decipher/data/web_scanning_events.json`, identifiable by the "Info" description starting with `[TEST]`, are present, and that the event "[TEST] Undefined: Research scanner inventory" contains two `research-scanner` objects.
6. In MISP, search for warninglists containing the IP address `66.240.192.138` ("Input filters" $\rightarrow$ "Warninglists" $\rightarrow$ "Search in Warninglists") and note the names as `<scanner-wl>`.
7. Run `rm -rf .venv-pymisp` in `tests/decipher/runners` to remove the Python environment created for pushing events to MISP.

## Expected outcome

### AC1, AC2, AC5: Analysis with matching threat intelligence
1. The following holds in the response:
    - `analyzed_scenario` is `suspicious_nt_scanning`.
    - `severity` is approximately 0.987.
    - `report.misp_events_found` contains the IDs of the "SQL injection scanning campaign against public web apps".
    - `report.score_breakdown` contains a breakdown of the event with `event_id`, `score`, `severity`, `confidence` and an `attribute_breakdowns` list.
    - `report.identified-scanners` is an empty list, since the source IP address matches no known scanning source.
    - `created_case.id` is non-zero and `created_case.link` points to the created case.
2. The following holds in the case page:
    - The case has a `priority-level:severe` tag
    - The case description contains the section "Scenario", referring to suspicious network/web scanning, "Alert information" with the data sent in the POST request, "Severity score", "Score breakdown" with the per-event and per-attribute contributions, and "Additional information" with the `log_summary`, `identified-scanners`, `misp_available` and `misp_events_found` entries.
    - The description ends with a note stating that the `identified-scanners` field is contextual only and does not reduce the severity score.

### AC3: Warninglist match reported for a public scanning service
1. The following holds in the response:
    - `severity` is approximately 0.667.
    - `report.identified-scanners` contains one entry for the source IP address `66.240.192.138`, naming `<scanner-wl>` as the matching source.
    - `created_case.id` is non-zero.
2. The validation succeeds.

### AC3: Research scanner match reported from MISP objects
1. The following holds in the response:
    - `report.identified-scanners` contains an entry per source IP address, mapping `167.94.138.34` to the project and domain labels of the Censys `research-scanner` object and `141.212.123.17` to those of the University of Michigan one.
    - `report.misp_events_found` contains the ID of the research scanner inventory event.
    - `severity` is 0, since the undefined threat level of the matched event contributes no severity, and no priority threshold is reached.
    - `created_case.id` is non-zero: the case is created in spite of the zero score, because the known-scanner context is evidence for the analyst.
2. The case description contains the information of both matching IPs in the "identified-scanners" section.

### AC6: No matching threat intelligence
1. The following holds in the response:
    - `severity` is 0.
    - `report.misp_events_found` is an empty list and `report.score_breakdown` contains no event result.
    - `report.identified-scanners` is an empty list.
    - `created_case.id` is 0, `created_case.link` is an empty string and `report.log_summary` states that no case was created because no threat intelligence was found for the alert IOCs.
2. The response is as in step 1, except that `report.identified-scanners` contains an entry mapping `71.6.199.23` to `<scanner-wl>` and that a case is created, with `created_case.id` non-zero and a `priority-level:baseline-minor` tag. The severity score remains 0, that is, the known-scanner match does not raise it.
